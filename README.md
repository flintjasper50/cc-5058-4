# 营地居民效用决策沙盘

一个无构建依赖的浏览器沙盘：三位营地居民每拍根据**疲劳、饥饿、社交需求、任务压力**，在休息 / 取食 / 交流 / 工作 / 接待来客 / 紧急任务之间做选择，然后真的走到场景中的位置把动作做完。决策内核是确定性纯函数，没有随机数、没有系统时钟，所以整条轨迹可以重放。

## 启动界面

```bash
python3 -m http.server 8080
```

然后打开 <http://localhost:8080/>。（`npx serve .` 也可以；不要用 `file://` 直接打开，ES module 需要 HTTP。）

没有安装步骤：仓库里没有打包器，`index.html` 直接 `<script type="module" src="./src/app.js">`。

**图形界面是居民效用的主入口**：场景芯片、需求滑杆、设施开关、本拍求值表（效用/可行性/成本/迟滞/有效分）、承诺核验与策略比较都在浏览器里操作。命令行只做辅助复跑，不另算一套分数（见文末“命令行辅助核验”）。

## 接口怎么被驱动

界面不是脚本回放，所有控件都调用同一个内核：

- **播放 / 单拍 / 跑 60 拍** → `step(state, opts)`，每拍重新求值，写回 `state.decisions`。
- **需求滑杆 / 设施失效开关 / 新增来客 / 紧急任务** → `setNeed`、`setFacility`、`spawnVisitor`、`spawnEmergency`，下一拍自然进入效用求值。
- **转身接待 / 交接餐盘 / 把餐给来客 / 取消预约 / 改派** → `greetVisitor`、`handoffTray`、`handPlateToVisitor`、`cancelDining`、`reassign`。失败会返回带理由的对象，界面显示这条理由并把判断交回居民效用。
- **核验房主承诺** → `verifyPromise`，用双方饥饿变化、餐份去向、浪费量、抵达延迟来判断，而不是读承诺文本。
- **策略比较** → `comparePolicies`，在阈值场景上并行跑“无迟滞 / 仅迟滞 / 仅承诺”三种策略，各 80 拍。

## 三种分数是分开算的

| 层 | 函数 | 作用 |
| --- | --- | --- |
| 效用 | `utilityFor` | 这个活动有多想做 |
| 可行性 | `feasibilityFor` | 结构性阻碍（设施失效、端盘冲突、无座位……） |
| 执行成本 | `costFor` | 路程、排队等待、疲劳风险 |

`有效分 = 效用 + 迟滞 + 承诺加成 − 切换代价 − 执行成本`。**只有可行活动能被选中**，所以高需求但不可达的目标（例如灶台失效时的取食）不会因为分数高而胜出。界面逐行展示每项贡献与不可行原因。

## 迟滞 vs 承诺时窗 vs 改派边际

三者都抑制抖动，但机制和代价不同，界面的“策略比较”用同一初始场景量化：

- **迟滞**：留在当前行动本身更划算（`hysteresisBase × decay^连续拍数`），随停留时间衰减。
- **切换代价**：每次换岗固定扣分。
- **改派边际（惯性，`switchMargin`）**：动作已经在途/执行中时，替代活动的有效分必须**领先当前活动超过这个边际**才允许改派；它不是锁——动作自然结束、目标变不可行或紧急任务出现时，下一拍照常自由重选。
- **承诺时窗**：开局锁定到 `t + commitmentTicks`，窗口内不改主意。

为什么需要改派边际：当两条需求曲线在阈值附近反复交替时，只靠逐拍取最高分会让角色在两条路线之间来回中断，动作永远做不完（修复前“无迟滞/无承诺”策略 80 拍出现 3 次 4 拍内反复）。边际门槛按“改派是否值得”而不是“谁此刻高 0.01 分”决定，因此**不锁死任何活动**，完成的行为效果也只在完成时结算一次，不会因重新选择重复施加。

阈值场景被调成饥饿与社交真正反复交替（长动作 + 接近的初始值），因此各机制会产生不同轨迹。在默认参数、80 拍下实测（同一确定性欲望轨迹）：

| 策略 | 饥饿上界 | 换岗 | 4 拍内反复 |
| --- | --- | --- | --- |
| 无迟滞 / 无承诺（仅惯性边际兜底） | 82.3 | 13 | 0 |
| 仅迟滞 + 切换代价 | 83.3 | 11 | 0 |
| 仅承诺窗口 10 拍 | 83.1 | 12 | 0 |

**换岗更少往往伴随更高的饥饿上界**——窗口越长、惯性越强，居民越可能守着旧行动挨饿。这正是“别把某个总分高当成唯一合理行为”的取舍，所以要把换岗次数和需求变化放在一起看，而不是只看换岗次数。

## 场景

`equal-mealtime` 双人同值饭点 · `threshold` 阈值迟滞 · `facility-fail` 设施失效 · `emergency` 突发紧急任务 · `two-plate` 两人份餐盘 · `greeting` 排队时接待来客 · `promise-delay` 来客迟一拍。

每个场景只设定初始条件；之后的每一步仍由同一个效用内核决定，没有任何写死的日程轮播。

## 关键状态约定

- 动作效果**完成时才结算**，执行途中不预扣；完成后进入 idle，下一拍自由重选，已结算的效果不会因重选重复施加。
- 失败与中断走 `failAction` / `abandonAction`，记入 `metrics.failures` / `metrics.interrupts` 并写事件流。
- 失败当拍有一拍冷却（`failedAtTick`），不会在同一拍立刻重选刚失败的活动——否则排队失败会重建餐桌预约并重复计数；下一拍恢复正常求值。
- `failAction` 同时释放排队/在途阶段留下的餐桌 `reservations`，避免人已离开却仍占住座位的“幽灵预约”。
- 在途（`incoming`）来客不产生任何效用；已到门口的来客只给**真正能接待**（有承诺或社交需求达标且未端盘/未入座）的居民增加接待拉力，其他人的交谈效用不会被凭空抬高。
- 端着两份餐盘且同伴已坐下时，改派会被挡住，必须先交接餐盘或取消同伴预约。
- 来客“下一拍抵达”由 `arrivalTick = startedTick + 1` 落实；承诺是否兑付从真实状态变化判定。

## 测试

```bash
npm test        # node --test，31 个用例
```

覆盖分层求值、不可达目标不被选中、效果不在执行中预扣、排队可转身接待、两人份改派冲突、承诺一拍延迟与违约检测、迟滞与承诺的取舍、紧急任务、设施失效、逐项贡献展示、确定性重放，以及活动抖动回归（阈值微扰不逐拍打断、惯性小差距保持/大差距改派、完成后不锁活动、失败释放幽灵预约且只计一次、在途与无资格来客不制造虚假效用、完成效果不重复结算）。

浏览器图形入口另有端到端回归（先 `python3 -m http.server 8080`，再 `npm run test:e2e`），通过真实页面驱动阈值场景、策略比较、需求滑杆与设施失效开关，断言界面分数来自修补后的内核且无页面报错。

## 命令行辅助核验

图形界面（`index.html` 的场景芯片、滑杆、本拍求值表与“策略比较”按钮）是居民效用的主入口；命令行只调用同一内核复跑并打印证据，异常判断仍以界面的“不可行/保持原因”提示为准：

```bash
npm run utility -- --scenario threshold --ticks 80 --compare
npm run utility -- --scenario equal-mealtime --ticks 40 --resident lin
```

输出每个居民的需求变化、本拍各活动的效用与有效分（实际运算值）、选中项与保持原因，以及换岗次数、4 拍内反复、失败与浪费等执行证据；存在失败时逐条列出失败事件。
